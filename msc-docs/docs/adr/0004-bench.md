# 0004: Benchmark design and the core's tool log

Date: 2026-11-10. Status: accepted. Module: [msc-bench](../../../msc-bench/README.md).

## Context

The plan measures quality, speed and tokens with and without the toolset, and sets targets only after a baseline run. The bench must work before msc-core exists (baseline), must judge both modes with the same checks, and must not depend on core's code.

## Decision

- **Agent:** Claude Code run headless (`claude -p --output-format json`; newer versions print an array of events, older ones one result object). Its result gives turns, token usage (input, cache write, cache read, output) and cost for both modes. The command is configurable in `msc-bench/bench.json`.
- **Modes:** both modes run with `--setting-sources project,local`, so the user's own plugins, skills and memory on the bench machine do not leak into either run. Project memory is a setting source the bench keeps, and Claude Code reads `CLAUDE.md`, `CLAUDE.local.md` and `.claude/CLAUDE.md` from the working folder and every folder above it, so attempts run under `~/.msc/bench-runs` by default, outside this repository (under `msc-bench-runs` in the system's temporary folder when the home folder is itself inside a project, such as a dotfiles repository), and `run` refuses an `--out` folder that has such a file or a `.git` in it or above it, checking the path with symbolic links and `..` resolved as the system resolves them and then writing to that resolved folder; until 2026-11-13 the default was `msc-bench/runs`, which gave both modes the repository's own CLAUDE.md and sources (#299). `baseline` runs with `--strict-mcp-config` and no MCP servers; `toolset` adds an MCP config that starts msc-core and requires (`requireMcp`) that Claude Code's init event lists `msc` as connected; Claude Code `-p` sometimes starts the session before an MCP server connects (seen on the PC, 2026-11-12), so such an attempt is retried up to 3 times rather than scored. Because Claude Code connects MCP servers in the background, the init event can list none even when the tools arrive a moment later (two false retries in the first full run); an attempt whose tool log has any call counts as connected. The model is pinned (`--model claude-sonnet-4-6`) so runs on different machines and days compare. Everything else (fixtures, prompt, checks, time limit) is identical.
- **Checks are toolset-independent:** files, build commands, PNG and zip inspection, and the live server over vanilla RCON (`execute if block` for blocks). No check uses msc-core or the agent plugin. Game-scale tasks add tests the agent never saw (`addFiles`, run with the project's own Gradle build) and a `player` check: msc-bot's test player, used as a library, joins the server jar the workspace built and plays a script, with console replies read from standard output.
- **Platforms (2026-11-12, roadmap R7):** a task is `paper` or `minestom`. Minestom tasks start from a scaffolded msc-templates project and run no Mojang server, so they need no EULA and can run on any machine; the first is `game-sky-sprint`, a whole minigame scored by hidden `@EnvTest` rules and a test player.
- **World tasks:** the runner starts the Paper server and runs setup commands before the agent, so both modes start from the same world. In toolset mode the server gets `MSC_CORE_ADDRESS` and `MSC_TOKEN`, and core listens there and accepts the agent that connects (agreed with msc-core).
- **Paper jar:** found in the jar caches (msc-bench `.cache/`, then msc-core's `.msc/cache`) or downloaded from PaperMC's Fill API, so a run needs no setup. Toolset workspaces get the jar pre-seeded in `.msc/cache` and core runs with `MSC_SERVER_DIR=<workspace>/server`, so both modes use the same server folder and neither pays for a download.
- **Server files:** the files Paper's launcher downloads on first start (`cache/`, `libraries/`, `versions/`) are saved once from a server that reached RCON and copied into later workspaces, so no task depends on a fresh Mojang download (the first baseline lost a task to a truncated one). A server that exits during start is retried once.
- **Metrics:** wall time of the agent process, pass (all checks), turns, total tokens, output tokens, cost, tool calls. Reports use medians per task.
- **Tool log (format v1):** msc-core appends one JSON object per finished MCP tool call to the file named by `MSC_TOOL_LOG` (default `<workspace>/.msc/tool-calls.jsonl`), flushed per line. Fields: `v` (1), `ts` (ISO-8601 finish time), `tool`, `ok`, `durationMs`, `argsChars`, `resultChars`, `resultTokens` (ceil(resultChars/4) in v1), optional `imageTokens` (estimated tokens of images a tool returned, such as `world_render`), optional `error`. Readers ignore unknown fields and skip lines with another `v`, so core can add fields freely; incompatible changes bump `v`.
- **Safety:** the agent runs with `--dangerously-skip-permissions` because runs are unattended; each attempt has its own folder, and the README says to run the bench only where that is acceptable. The runner tracks every process it starts (agent, server, check processes) and a shutdown hook kills them with their descendants when a run is cut short (Ctrl-C ends the JVM without its `finally` blocks), then sends `stop` to whatever answers on the bench's RCON port; a server task first stops a server left on the bench's ports, so setup and checks never reach another run's world (#300). The Minecraft EULA is never accepted by the bench: `server.acceptEula` comes only from the owner's machine-wide acceptance in `~/.msc/eula.json` (msc-core's format), never from a config file, and without it Paper server tasks are skipped. (Until 2026-11-12 it came from an untracked `bench.local.json`; that file is no longer read.)
- **Usage limits:** an agent run that ends on an account usage limit (API error 429) stops the whole run, unrecorded. The first full run lost 36 attempts to one, each failing in seconds.

## Consequences

- Minestom tasks run anywhere; Paper tasks run where the owner accepted the EULA; toolset runs need core and the agent jar built.
- Token counts include the model's whole context, so they capture both smaller tool results and fewer turns.
- Targets were set from the first full run (2026-11-12) and recorded in the plan's Goal and success metrics.
