# ADR 0012: CI/CD on GitHub Actions and Dependabot

Status: accepted, 2026-11-12. Decided by Claude under Jeremiah's hand-over of build decisions.

## Context

The repository is on GitHub (private) and several threads now push branches and open pull requests in parallel. Nothing checked a change before it reached `main`, dependency updates were manual, and there was no way to hand someone a built toolset. Private repositories pay for Actions minutes, so the setup has to stay lean.

## Decisions

1. **CI: `./gradlew build` on Java 25, on Linux and Windows.** `.github/workflows/ci.yml` runs on pushes to `main`, on every pull request and by hand. It builds and tests every module with Temurin 25 on `ubuntu-latest` and `windows-latest` (a two-entry matrix, `fail-fast: false`, every step in Git Bash). No further split: the build is one Gradle invocation that already runs modules in parallel, and every extra job pays the start-up and cache-restore cost again. *Amended 2026-11-12 (roadmap N4):* the first version ran Ubuntu only; the owner develops on Windows and #29 was a Windows-only test failure found on the PC, so Windows joined the matrix. Windows minutes cost twice Linux minutes on private repositories; that is the price of catching such failures on every PR instead of in an integrator round.
2. **What CI does not run.** The default `test` task excludes the `template-build` tag (`:msc-templates:verifyTemplates` scaffolds each template and runs its own Gradle build, several minutes each), so CI leaves it out. No step starts a real Minecraft server, and no step writes `eula.txt` or passes an EULA flag: accepting Mojang's EULA stays a decision for a person, never for CI. Tests that download things only reach public build repositories (Maven Central, PaperMC, Fabric, Mojang's library metadata through Loom), which runners reach.
3. **Caching through `gradle/actions/setup-gradle`.** It caches the wrapper, dependencies and Loom's Minecraft files, and only `main` writes the cache; branches and pull requests read it. The repo's `org.gradle.caching` and configuration cache stay on.
4. **Minutes.** Changes that touch only documentation (`docs/**` including the wiki source, `msc-docs/**`, root `*.md`, module `README.md`/`PLAN.md`) skip CI. A newer push to the same branch or pull request cancels the older run; runs on `main` are never cancelled. Jobs time out after 30 minutes. Test reports are uploaded only on failure and kept 7 days.
5. **Dependabot, weekly and grouped.** `.github/dependabot.yml` checks Gradle (the version catalog and settings plugins) and GitHub Actions every Monday. Gradle updates come as at most two PRs: `minecraft-platforms` (Paper, Fabric, Loom, Minestom, MockBukkit, Mojang) because those move with the Minecraft version and must be updated together, and `libraries-and-plugins` for everything else. Actions updates come as one PR.
6. **Release on version tags, or by hand.** Pushing a tag `vX.Y.Z` (or `vX.Y.Z-suffix`, published as a pre-release) runs `.github/workflows/release.yml`. So does running it by hand on `main` with a version (Actions tab, or the API), which is how cloud sessions release: their git access cannot push tags, so the workflow creates the tag on the commit it built. It refuses a version whose tag already exists. Either way it runs `./gradlew build -Pversion=X.Y.Z`, then a GitHub Release with generated notes and these files:
   - `msc-core-X.Y.Z.zip`, the MCP server distribution from the application plugin (`bin/msc-core` launchers and `lib/`, templates included);
   - `msc-agent-paper-X.Y.Z.jar`, `msc-agent-fabric-X.Y.Z.jar`, `msc-agent-minestom-X.Y.Z.jar`, the agent jars with msc-protocol inside;
   - `SHA256SUMS.txt`.
   The release builds and tests again from the tag, so a release can never ship untested code. `gradle.properties` keeps `0.1.0-SNAPSHOT` for local builds; the tag sets the released version. Release notes are GitHub's generated PR list, with hand-written highlights from `msc-docs/releases/vX.Y.Z.md` above it when that file exists.
7. **Pinned by major version, one style for every workflow.** Actions are referenced by major tag (`actions/checkout@v7`, `actions/setup-java@v6`, `gradle/actions/setup-gradle@v6`, `actions/upload-artifact@v7`) and Dependabot moves them. The release uses the preinstalled `gh` CLI instead of a third-party release action. Dependabot also keeps the wiki-sync workflow (`wiki.yml`, from the wiki work) on current majors; CI does not duplicate it.

## Consequences

- Every pull request shows a build status; the CI/CD thread watches it and fixes breakage.
- Dependabot cannot keep the two Loom pins in step (the catalog's `fabric-loom` version and the plugin version in `settings.gradle.kts`), nor versions that only feed templates (`foojay`, `slf4j`). Those stay manual, as does Paper's `26.3.build.+`, which already takes the newest build.
- When the usable-v1 work changes the shape of the `msc-core` distribution (for example agent jars inside it), the release picks that up with no workflow change.
- Branch protection (requiring CI to pass before merging) is a repository setting and is not part of this change.
