# MCP tool catalogue

The AI talks to `msc-core` over MCP (stdio). This page lists every tool, its arguments and what its result looks like. Design reasons are in [ADR 0005](adr/0005-core-tools.md).

The tool tables are generated from the tool definitions in `msc-core` (`io.github.imnotstable.msc.core.tools`): the "What it does" column and the argument texts are exactly what the AI sees. Do not edit between the `<!-- tools: ... -->` and `<!-- /tools -->` markers; change the code and run `./gradlew :msc-core:toolDocs`. `./gradlew build` fails while this page or the wiki's tool page is out of date ([ADR 0026](adr/0026-generated-tool-docs.md)). Everything outside the markers, such as the "Results" notes, is written by hand.

## Rules every tool follows

- Results are plain text, no Markdown and no JSON, shaped to be read by a model.
- Every result has a size budget. One token is counted as four characters. The default cap is 6,000 characters (about 1,500 tokens); tools with a `maxChars` argument accept 200 to 24,000 and refuse other values. A cut result ends with `[truncated: N more lines, M chars. <what to do>]`, and that line is inside the cap. A cut end of the log (`server_logs` mode=tail and mode=grep, the console lines of `server_command`, the last lines of `server_wait` and of a `server_start` or `dev_cycle` that exited, an installer's output in a `server_setup` error) keeps its newest lines and starts with `[truncated: N earlier lines, M chars. <what to do>]` instead; the line counts every line dropped wholly or partly. The tool registry applies the cap to every result, errors included, so no tool can exceed it. A tool spends the cap as one budget: a result of several parts (`dev_cycle`'s failed tests and startup log, `server_start`'s header and startup log, the outputs of several `server_command` commands, a `texture` drawing and the lines around it) keeps its fixed lines and its documented last line, and spends the rest on its parts: first parts are shown whole, smallest first, as many as fit beside the short line that counts the rest; the rest share what is left, each cut to its share with its own hint when every share is at least 80 characters, otherwise as many as get 80 or more are cut and the others show `[cut]` (or nothing, when not every marker fits), and one line before the last line says `[N of M outputs cut to fit. <what to do>]`, counting every part not shown whole (`[N of M outputs cut]` when the hint does not fit). So no output is left out or cut while the room left over would have shown it whole. A part cut so short that its `[truncated: ...]` line does not fit ends in `[M chars cut]` instead. The registry's cut (`Narrow the call.`) is only the safety net for a result that still came out longer.
- String arguments are one line: a control character (NUL, a line break, a bell) is refused with `error: argument <name> has a control character (U+....)`. The exceptions are `build_batch`'s `steps` and `server_command`'s `command`, which may be several lines (line breaks and tabs only), and `pack`'s `description`, which may have one line break (Minecraft shows a pack description on two lines; a third line, a tab or any other control character is refused).
- Path arguments (`project_scaffold dir`, `dev_cycle project`, `structure_save file`, `world_summary diff`, `build_batch`'s `file=`, `pack file`, a `.png` `texture name`) are relative to the workspace and must stay inside it once `..` is applied; only `msc_workspace`'s `path` may name a folder anywhere. So `dev_cycle` builds only a project inside the workspace: to work on one elsewhere, switch to its folder with `msc_workspace`. A path the file system cannot hold (a control character, a name longer than 255 bytes, a character the platform refuses) is refused in one line naming the argument, before anything is written; a folder that cannot be created is refused in one line naming the folder and the reason. No tool answers `error: internal: ...` for bad input (`BadInputBehaviourTest` calls every tool with every string argument set to such values).
- Arguments are checked in one place, `ToolRegistry.call`, before the tool runs, so a refused call changes nothing, is logged and is counted in `msc_status stats=true` like any other: an argument the tool does not take is refused with the ones it does take (`error: unknown argument x; world_slice takes region, world, states, maxChars`), a missing required one with `error: missing argument: <name>`, a value of the wrong JSON type with `error: argument <name> must be an integer` (or a number, true or false, a string, an array of strings). Numbers and booleans may also come as strings (`"5"`, `"true"`). The MCP SDK's own schema check is off (#510), so no call is answered by it; the SDK still answers two requests itself, as JSON-RPC errors the MCP spec calls protocol errors: a tool name that is not in the list, and an `arguments` value that is not an object.
- A tool that picks a way refuses an argument that way does not read, in one line and before it does anything, instead of dropping it with an OK: `server_logs` by `mode` (`error: pattern is for mode=grep; add mode=grep or leave it out`; `lines` is for tail and grep), `texture` by rows, `kind`, `copy` or `animate`, `pack` by `check`, `build_batch` by `dryRun` (`physics` places nothing in a dry run), `msc_workspace` by `path` (`create`), and `server_setup` by platform (`version`, `mode` and `acceptEula` are not for minestom or velocity).
- A number's range is declared once, in the schema's `minimum` and `maximum` (shown in the tables as `(integer, 1 to 100)`); a value outside it is refused with the range (`error: argument limit must be 1 to 100, not 101`), never clamped silently. The tables are generated from the same declaration, so the stated and the checked range cannot differ.
- Structure files: `structure_save` writes a Sponge schematic and takes only a `file` ending in `.schem` (any case). `world_summary diff=` and `build_batch`'s `file=` go by the content, not the name: a gzip file is read as a schematic, anything else as a UTF-8 text structure; a file that is neither is refused in one line naming it.
- Errors come back as `error: <what is wrong and what to do>` with MCP `isError` set. They never contain a Java stack trace.
- Coordinates are strings: a position is `"x,y,z"`, a region is `"x1,y1,z1 x2,y2,z2"` (two corners, inclusive, any order), an area is `"x1,z1 x2,z2"`.
- Block names may omit `minecraft:`. Properties use vanilla syntax: `oak_stairs[facing=north]`.
- `world` is optional everywhere and defaults to the server's first world.
- Every call is logged (see "Tool log").
- World and build tools fail at once with `error: the server is not running...` when the core has no server running and none was attached with `MSC_CORE_ADDRESS`.
- <!-- tool-list -->The tool definitions (26 tools: names, descriptions, argument schemas) are 15,867 characters, about 3,967 tokens in every conversation before MCP framing.<!-- /tool-list --> `McpBridgeTest` fails if the tool list as the client receives it grows past 16,000 characters ([ADR 0019](adr/0019-smaller-tool-surface.md), [ADR 0023](adr/0023-texture-tools.md)).
- Results are text. The one exception is `world_render`, which adds one PNG image next to its text.

## Typical loop

`project_scaffold` once, `server_setup` once, then edit code and call `dev_cycle` until it reports `no errors or warnings`. Look names up with `api_search` instead of guessing. Look at the world with `world_summary`, then `world_slice`; build with `build_batch`, a whole build per call.

Results:

- `msc_status`: 6 to 8 lines: core version, workspace, platform, server state (`running, detached`, `running, left by an earlier session` with its pid, or `running under another session that is still running` with the server's and that session's core pid, ADR 0037), agent, API index, then one line per setup warning: the workspace is the MSC repo, and the install is older than its checkout or a newer install sits beside it. The same warnings go in front of the session's first tool result, inside its cap: they share it with the result, and a warning cut to its share ends `msc_status shows it all.` With `stats=true`, a table of this session's calls per tool instead.
- `msc_workspace`: 1 to 3 lines. Without `path`, or with the current one, 1 line (`workspace: <path>` or `workspace is already <path>`). A switch: `workspace: <path>`, then a line on the old workspace's dev server only when one ran (`stopped the dev server of ...`, or that its detached server keeps running), then `server folder: ...; platform: ...`. Closes the old workspace like a session end and opens the new one; the server folder and tool log move along when they were the defaults. A relative `path` is relative to the current workspace.

Results:

- `project_scaffold`: 5 to 7 lines: where the project was created, its `projectId`, `packageName` and `version`, then for NeoForge and Forge a line that the first build started in the background, then the next step: 1 line, or 2 when a server that needs the EULA (any platform but Minestom) is not set up and the EULA is not accepted for this machine (the EULA question, then `On yes: server_setup acceptEula=true, ...`). Remembers the template's platform for the workspace.
- `server_setup`: one line per step that has something to say, in this order: `wrote N default config files` (only the files the server folder lacked); with `mode`, `mode game: survival, normal difficulty from the next start` or `mode build: creative, peaceful difficulty from the next start`; the install (Paper `paper <version> build <n> (downloaded)` or `(cached)`; Purpur `purpur <version> build <n> (installed)` or `(already there)`; NeoForge and Forge `<name> <version> (installed)` or `(already there)`; Fabric `fabric launcher for ...` then `fabric api <version>`; Quilt `quilt loader <version> (installed)` then `fabric api <version>`); `agent installed in mods/` (or `plugins/`), or `warning: msc <agent> agent not found ...`, naming the agent the platform runs and the jar to put in `.msc/agent` (`msc-agent-paper.jar` for Paper and Purpur, `msc-agent-fabric.jar` for Fabric and Quilt); Paper or Purpur without Velocity forwarding, with Geyser wanted (`bedrock=true`, or a folder that has it): `geyser <version> build <n> (downloaded), floodgate ...` (or `(cached)`, `(already there)`; `geyser (already there)` for a jar kept while GeyserMC is down), `bedrock.port was taken, moved to N` when it was, and `bedrock: UDP <address>:<port> (Geyser, fronting Java port <port>; ...)`; `bedrock=false`: `removed Geyser and Floodgate from plugins/ (their config folders stay)`; the EULA: `eula.txt has eula=true from the owner's one-time acceptance for this machine (...)`, or `note: eula.txt has eula=true; ...` when the file already says so, or when it is not accepted two lines, `the Minecraft EULA is not accepted, so server_start refuses. Next: ask the user ...` and `On yes: server_setup acceptEula=true ...`; the first `acceptEula=true` adds `Minecraft EULA (...) accepted for this machine ...` before the EULA line; last `<platform> server ready in <folder>; next: server_start or dev_cycle`. Minestom: `minestom needs no server download ...`. `mode=game` sets `gamemode=survival`, `difficulty=normal` and `force-gamemode=true` in `server.properties` (`mode=build`: creative, peaceful); without `mode` a new server gets build defaults and an existing one keeps its settings. Folia (ADR 0045): Folia `folia <version> build <n> (downloaded)` or `(cached)`, then `folia: plugins load only with folia-supported: true ...`. With `proxy` (Paper, Purpur, Folia), before the install line: `proxy velocity: players join only through the Velocity proxy ...` or `proxy none: players join directly`. Velocity: Velocity `velocity <version> build <n> (downloaded)` or `(cached)`, `wrote velocity.toml: ...` (or `velocity.toml kept as it is`), `backend: a paper, purpur or folia server set up with proxy=velocity, ...`, last `velocity proxy ready in <folder> ...`.
- `server_start`: up to 6,000 chars: `server ready in 8.2s, agent connected`, then `world world: ground is y=-61 (most common top block around 0,0; build from y=-60)` (dev worlds are superflat, far below y=64), then `mode: creative, peaceful difficulty (server_setup mode=game for survival, normal: ...)` from `server.properties`, then, with Geyser in `plugins/` where it works (Paper or Purpur, Velocity forwarding off), the `bedrock: UDP ...` line `server_setup` gives, plus startup warnings and errors only. A server that exits during or right after startup is reported as `server exited ...`, then its triage (below), then its warnings and errors. Fails at once with a one-line error, before it changes anything, if there is no server to start or `eula.txt` lacks `eula=true` and the EULA is not accepted for this machine (nor with `acceptEula=true` on this call). Replaces an installed agent jar that differs from the one in `.msc/agent` (or `MSC_AGENT_JAR`) first, and says `agent jar updated`. Just before the start, also removes what an interrupted earlier call left in `plugins/`, `mods/` or `libs/` (such as `x.jar.msc-removing` from older cores, which Quilt would load as a second copy of the mod) and says `removed N files an interrupted earlier call left`.
- `server_detach`: 2 or 3 lines: `server detached: ...`, then `server.properties now offers the pack too, ...` only when a built pack's host keeps running and the server folder has a `server.properties`, then that world tools work until the session ends. The pack host, if a pack was built, moves to a standalone process on the same port (pid in `.msc/pack-host.pid`), and `resource-pack`, `resource-pack-sha1`, `resource-pack-id` and `require-resource-pack` go into `server.properties`, so a restart outside MSC still sends the pack. The server keeps this session as its owner: while this session runs, another session's tools refuse to touch it (ADR 0037). Once it ends, the next `server_start`, `dev_cycle` or `server_stop` stops both, the server over RCON; the next start serves the pack again on the same port and updates `server.properties` (or clears it if the pack is gone).
- `server_stop`: 1 line. Also stops a server an earlier core left running (pid and start time in `.msc/server.pid`, with the pid and start time of the core that started it), as `server_start` and `dev_cycle` do first: over RCON so it saves (at `server-ip` and `rcon.port` from `server.properties`, read as the server reads them), killed only if that fails. The pid file stays until that server is gone. A leftover that survives the kill is an error naming its pid, what was tried and how to stop it by hand; while it runs, `server_start` and `dev_cycle` refuse too (a new server could not take its world or port, and its pid would replace the leftover's record), and only kill it again briefly instead of waiting the whole stop out again (`resisting` in the pid file). `server_stop` tries the whole stop again each time. A server whose core still runs (another session open on the same workspace) is no leftover: `server_start`, `server_stop`, `dev_cycle` and `server_setup` then refuse in one line naming that session's core pid (use that session, or end it) and change nothing (ADR 0037). A pid file from cores before that names no owner and is a leftover as before. Every change a core makes to the pid file (a start's check, launch and record; a stop's delete; a leftover's claim) is made holding a short lock on `.msc/server.lock`, so two sessions starting at the same moment launch one server and the other is refused as above; a call that waits over 10 s for another session's start or stop refuses in one line and changes nothing.
- `dev_cycle`: up to `maxChars`. Gradle builds only the deployable jar (`mscJar`, added by `.msc/msc-init.gradle`; on Minestom a thin `server.jar` plus `libs/`), then the tests (`check`) run while the server restarts. A jar identical to the one the running server loaded is not redeployed and the server keeps running. When the server it restarts would refuse to start (the EULA not accepted), it refuses at once with that one-line error, before building or changing anything. On a failed compile: compiler errors. Failed tests come first (`TESTS FAILED`; the new jar is deployed anyway). Then startup warnings and errors, or `no errors or warnings`, and a last line `time: jar, stop, start, agent, tests, total`. A cut of its own lines, or its `[N of M outputs cut to fit. ...]` line, names only what shows what was cut: `Failed tests: <project>/build/test-results.` when this run's tests wrote results there, `Startup log: server_logs.` after a start, then raising maxChars below 24,000.
- `server_logs`: up to `maxChars`; see "How logs are condensed" and "How crashes are triaged" below.
- `server_command`: up to 6,000 chars. A command with bad syntax fails with the parser's message (`command failed`, then where it stopped). Lines the server console printed while the command ran (broadcasts such as `/say`, which never reach the sender) follow under `console during the command:`.
- `server_wait`: 1 to 6 lines: `matched after 4.1s: <line>`, or `no line matched in 60s` (or `the server stopped after ...`) followed by up to the last 5 new lines. Looks at lines since the last `server_command`, `server_wait` match or start, so a line printed between two calls is not missed and one line never matches twice. Not an error on timeout. `timeoutSeconds` is at most 600. Only for a server this core started.

How logs are condensed: the dev server's fixed banners (running as root or administrator, offline mode) and the Windows system-report noise (`[oshi.*]` messages, `Failed to get system info for ...`) are dropped. Otherwise only WARN and ERROR entries and anything with a stack trace are kept. In a trace, the exception lines, the first frame and all frames outside framework packages (`java.`, `net.minecraft.`, `org.bukkit.`, `io.papermc.`, the mod loaders' `net.fabricmc.`, `net.neoforged.`, `net.minecraftforge.`, `cpw.mods.`, Velocity's `com.velocitypowered.`, Minestom's `net.minestom.`, Geyser's `org.geysermc.`, Mixin and similar: each platform's own packages) are kept; runs of framework frames become `... N framework frames`. Identical entries are shown once with a count. By default `server_logs` looks only at lines since the last start.

How crashes are triaged (`server_logs mode=triage`, and `server_start` and `dev_cycle` when the server exits; [ADR 0040](adr/0040-crash-triage.md)): at most 3 findings, each a few lines: what died and where it was read (`[log 12:00:02]`, a crash report's file name), `culprit:` (the first frame outside JDK, server and loader packages, or `server or loader code`), `cause:` (the root exception: the last `Caused by`), up to 3 key frames, and a one-line `fix:`. It reads the log since the last start (the whole buffer with `all=true`; `logs/latest.log` when the buffer is empty), the newest `crash-reports/crash-*.txt` and the newest `hs_err_pid*.log` written since the last start (any with `all=true`). Known causes come first, from the messages each platform prints: the EULA, the server's port in use (`FAILED TO BIND TO PORT`, or a bind under server code; the fix names `server-port` in `server.properties`, on Minestom the main class's `server.start(...)`; a port a plugin or mod binds itself is that code's exception), out of memory, a wrong Java version, a missing or wrong-version dependency (Paper and Purpur, Fabric and Quilt, NeoForge and Forge), a plugin that failed to enable or load, a mod whose entrypoint, constructor or mixin failed, the watchdog. A known cause with no plugin or mod frames is one line and its fix. Otherwise the fatal or uncaught exception, or with none the last logged exception (`not fatal`). A crash report that holds the log's exception joins its finding; repeats are counted (`(x2)`). Nothing found: `no crash or startup failure found in N log lines and no new crash report; server running` (or `not running`), or `... in N lines of logs/latest.log ...` when it read that file. Repeats are counted on every platform, Minestom's untimed lines too.

### Platforms

The workspace has one platform: `paper` (default), `purpur`, `folia`, `fabric`, `quilt`, `neoforge`, `forge`, `minestom` or the `velocity` proxy ([ADR 0027](adr/0027-more-platforms.md), [ADR 0045](adr/0045-folia-and-proxies.md)). `project_scaffold` remembers the template's platform in `<workspace>/.msc/platform`, `server_setup platform=...` sets it, and without either the core looks at the project files, first match wins. First the descriptor the server loads, in `src/main/resources` or `src/main/templates` (the NeoForge MDK's), or the Gradle plugin that writes it: `quilt.mod.json` is Quilt, `fabric.mod.json` Fabric, `META-INF/neoforge.mods.toml` NeoForge, `META-INF/mods.toml` Forge, `paper-plugin.yml` or `plugin.yml` Paper (also written by plugin-yml's `bukkit`/`paper` plugin or block, or resource-factory's Bukkit or Paper convention), `velocity-plugin.json` Velocity. Then the platform's Gradle plugin in `build.gradle(.kts)` or `gradle/libs.versions.toml`: Quilt or Fabric Loom, ModDevGradle (its `legacyforge` plugin is Forge) or NeoGradle, ForgeGradle, paperweight or run-paper, run-velocity. Last a dependency: `velocity-api` Velocity, Minestom. So a plugin built for both Paper and Velocity is Paper. Purpur and Folia cannot be told from a Paper plugin, so they are only ever the remembered platform; `dev_cycle` keeps a remembered Purpur, Folia or Quilt for a Paper or Fabric project.

The backend of a Velocity proxy is a `paper`, `purpur` or `folia` server in its own workspace, set up with `server_setup proxy=velocity`: `config/paper-global.yml` gets `proxies.velocity` `enabled: true`, `online-mode: false` and the machine's secret (only those keys change; the file is written when missing), so players join it only through the proxy, the test player included; `proxy=none` turns it off. A proxy runs no world and no agent: world, build and player tools on it answer one line saying so, and `server_command` goes to its console.

Installers and downloads are cached in `.msc/cache`; Paper, Folia, Velocity and Purpur jars, which come with a checksum, are also kept in the machine's store (`~/.msc/downloads`, `MSC_DOWNLOAD_STORE`), so another workspace copies them instead of downloading them and `server_setup` reports them as already there (`(cached)` for Paper, `(already there)` for Purpur); an installer runs only when the server directory lacks that loader version. While a download service is down (unreachable, stalled, or answering 408, 429 or a 5xx), Paper, Folia, Velocity, Purpur, Geyser and Floodgate use the newest cached build, after a line `<service> answered <status> for <url>; using the newest cached build` (or `cannot reach ...`); with none cached, Geyser and Floodgate keep the jar already in `plugins/` (`<reason>; keeping the jar in plugins/`); otherwise `server_setup` fails. NeoForge, Forge and Quilt take the versions pinned in this build and `server_setup` refuses a Minecraft version they do not target.

Bedrock players ([ADR 0046](adr/0046-bedrock-players-through-geyser.md)): Geyser works only on Paper or Purpur without Velocity forwarding (a forwarding backend refuses direct joins, Geyser's too). There `server_setup bedrock=true` puts the newest Geyser-Spigot and Floodgate builds from GeyserMC's download API in `plugins/` (sha256-checked, cached and kept in the machine's store like Paper), and writes `plugins/Geyser-Spigot/config.yml` when it is missing: `bedrock.address` from `server-ip` (loopback for the dev defaults, so only this machine; `0.0.0.0` lets the LAN in), the first free UDP port from 19132, `auth-type: floodgate`. Later `server_setup` calls update both jars and keep the config, moving only a `bedrock.port` another program holds. Geyser-Spigot fronts the server it runs in, so its Java port is the server's own. Where Geyser cannot work, refused before anything changes: `bedrock=true` (`bedrock=true needs paper or purpur ...`, or `... does not work with proxy=velocity ...` with `proxy=velocity` or forwarding already on), and a setup that would keep Geyser already in `plugins/` (another platform, `proxy=velocity`, a plain setup of a forwarding backend): `Geyser is in plugins/ and <reason>: bedrock=false removes it`. `bedrock=false` removes the jars on any platform and keeps their folders. There is no Bedrock test client: `player_test` joins as Java only.

EULA step: installing or using MSC never accepts the Minecraft EULA. `server_setup` and `server_start` write `eula=true` into the server's `eula.txt` only on the owner's own yes: either `acceptEula=true` on that call, passed after the owner said yes, or the owner's one-time acceptance for the machine in `~/.msc/eula.json` ([ADR 0020](adr/0020-machine-eula.md)), and they say so. That file is written only on an explicit opt-in: `Main eula accept` run by the owner in their own terminal (the line in `~/.msc/core/eula-accept.txt`) with a typed `yes`, installing with `installMsc -Pmsc.acceptEula=true`, or the first `acceptEula=true` on `server_setup` or `server_start`; that first time the result says the acceptance now covers the machine. `project_scaffold acceptEula=true` does not write it.

## Testing a game

- `server_setup mode=game` before testing combat, damage or hunger: the default dev server is creative and peaceful, so mobs despawn and players take no damage.
- `world_entities` checks wave spawns, NPCs and holograms (text displays) without a player.
- `server_wait until="Wave 3"` waits for a log or chat line instead of polling `server_command`. Log what the game does (stage changes, wins, losses) so it can be waited for.
- `server_command "tick sprint 600"` runs 600 ticks (30 game seconds) as fast as the server can, so timers and waves come sooner. `tick rate 40` doubles the speed; `tick rate 20` restores it.
- Chunks with no player nearby are not loaded, so nothing in them moves: mobs spawned there freeze and redstone stops. Keep game areas loaded with a plugin chunk ticket (Paper: `world.addPluginChunkTicket(chunkX, chunkZ, plugin)`) or `forceload add x1 z1 x2 z2`. Vanilla spawner blocks and natural spawning also need a player close by, so spawn waves from the plugin.


## Text structure format

Used by `world_slice` (output) and `build_batch` `structure` steps (input), so a slice can be edited and written back.

```
legend: .=air #=stone_bricks g=glass
y=64
#####
#...#
#####
y=65 same as y=64
y=66 all #
```

- One character per block. Rows run from the lowest Z (top row) to the highest; columns from the lowest X (left) to the highest.
- `.` is air and `_` means "leave unchanged", unless the legend redefines them.
- Layers are listed by Y. In a `structure` step the numbers only give the order: the lowest layer is placed at the step's position.
- `y=N same as y=M` repeats a layer; `y=N all #` fills a layer with one symbol or block.
- Symbols are handed out by frequency. With `states=false` (default) blocks that differ only in properties share a symbol.
- `data X,Y,Z {SNBT}` gives the block there its block entity data, as `world_slice data=true` writes it. X and Z count from the `region` line's lowest corner when the text has one (a pasted slice does), else from 0 (first column, first row); Y is the layer number. The cell must hold a block, not `_`. Data turns with its block under `rotate`.

`build_batch` answers `edit eN: <count> blocks changed, region <box>`, plus a `blocks:` line when it placed more than one kind, for up to 8,388,608 blocks. The id undoes the whole edit, even when the core split it into several agent calls; ids are remembered for the life of the core process, but the server keeps only the last 8,388,608 changed blocks across all edits, so the oldest edits can be undone only partly (`undid eN partly: ...` says how many parts were lost). If an undo stops half-way (timeout, no server), the same id undoes the rest. An undo puts back block entity data too (sign text, container items) on every platform.

Block entity data ([ADR 0042](adr/0042-block-entity-data.md)): any block in a step may end in SNBT, as `/setblock` takes it: `set 3,-60,5 chest[facing=east]{Items:[{Slot:0b,id:"minecraft:diamond",count:3}],CustomName:'"Loot"'}`, `fill ... spawner{SpawnData:{entity:{id:"minecraft:zombie"}}}`. The core checks the SNBT first (`bad SNBT at character N: ...`, nothing placed) and drops `id`, `x`, `y` and `z`; the agent refuses data on a block that keeps none (`stone has no block entity data`). The data is merged into the placed block's data as `/data merge block` does, also where the block was already there, and the edit's undo puts the old data back. `copy` and `structure_save` keep block entity data (a schematic writes it as Sponge `BlockEntities`, with the block's id as `Id`), and a `structure` step from a `.schem` file (version 2 or 3) places it. `world_summary diff=` compares blocks only. Entities and items are not part of this: on every platform but Minestom, `server_command` reads and changes them with the game's own commands (`data get entity <uuid>`, `data merge entity <uuid> {...}`, `summon`, `give`, `item replace`); `world_entities ids=true` gives the UUIDs. Minestom has no entity or item NBT for the core to edit: the project's code makes them. `copy` reads the world before the call, so source and target may overlap. See [ADR 0015](adr/0015-build-batch.md) and [ADR 0019](adr/0019-smaller-tool-surface.md).

Undo ids do not survive a restart. For that, `build_undo backup=` keeps whole-world backups in `.msc/backups` (newest 5, within 2 GiB): `list` shows them (`<name> (<world folders>; <size>)`), `save [label]` takes one (`save-off`, `save-all flush`, copy, `save-on`), and a name (or a part only one name has; blank or ambiguous is refused) rolls the world back: `rolled back to <backup>`, `the world before it is backup <name>`, the stop note of a server an earlier session left running, as `server_start` gives it (that server counts as running, so it starts again), then the server's start report, or `server not started (it was not running)`. A `build_batch` of 100,000 blocks or more takes one first, unless one is younger than 5 minutes, and ends with `backup <name> taken first (build_undo backup=NAME restores it)`. Minestom saves its world only on stop, so a backup of a running Minestom server is the world as last stopped. See [ADR 0041](adr/0041-world-backups.md).
