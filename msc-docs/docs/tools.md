# MCP tool catalogue

The AI talks to `msc-core` over MCP (stdio). This page lists every tool, its arguments and what its result looks like. Design reasons are in [ADR 0005](adr/0005-core-tools.md).

The tool tables are generated from the tool definitions in `msc-core` (`io.github.imnotstable.msc.core.tools`): the "What it does" column and the argument texts are exactly what the AI sees. Do not edit between the `<!-- tools: ... -->` and `<!-- /tools -->` markers; change the code and run `./gradlew :msc-core:toolDocs`. `./gradlew build` fails while this page or the wiki's tool page is out of date ([ADR 0026](adr/0026-generated-tool-docs.md)). Everything outside the markers, such as the "Results" notes, is written by hand.

## Rules every tool follows

- Results are plain text, no Markdown and no JSON, shaped to be read by a model.
- Every result has a size budget. One token is counted as four characters. The default cap is 6,000 characters (about 1,500 tokens); tools with a `maxChars` argument accept 200 to 24,000 and refuse other values. A cut result ends with `[truncated: N more lines, M chars. <what to do>]`, and that line is inside the cap. A cut end of the log (`server_logs` mode=tail and mode=grep, the console lines of `server_command`, the last lines of `server_wait` and of a `server_start` or `dev_cycle` that exited, an installer's output in a `server_setup` error) keeps its newest lines and starts with `[truncated: N earlier lines, M chars. <what to do>]` instead; the line counts every line dropped wholly or partly. The tool registry applies the cap to every result, errors included, so no tool can exceed it. A tool spends the cap as one budget: a result of several parts (`dev_cycle`'s failed tests and startup log, `server_start`'s header and startup log, the outputs of several `server_command` commands, a `texture` drawing and the lines around it) keeps its fixed lines and its documented last line, and spends the rest on its parts: first parts are shown whole, smallest first, as many as fit beside the short line that counts the rest; the rest share what is left, each cut to its share with its own hint when every share is at least 80 characters, otherwise as many as get 80 or more are cut and the others show `[cut]` (or nothing, when not every marker fits), and one line before the last line says `[N of M outputs cut to fit. <what to do>]`, counting every part not shown whole (`[N of M outputs cut]` when the hint does not fit). So no output is left out or cut while the room left over would have shown it whole. A part cut so short that its `[truncated: ...]` line does not fit ends in `[M chars cut]` instead. The registry's cut (`Narrow the call.`) is only the safety net for a result that still came out longer.
- String arguments are one line: a control character (NUL, a line break, a bell) is refused with `error: argument <name> has a control character (U+....)`. The exceptions are `build_batch`'s `steps` and `server_command`'s `command`, which may be several lines (line breaks and tabs only), and `pack`'s `description`, which may have one line break (Minecraft shows a pack description on two lines; a third line, a tab or any other control character is refused). An array argument (`player_test`'s `actions`, `texture`'s `palette` and `rows`, `model_create`'s `textures`) takes a line break as the end of an item: `actions="say hi\nwait 20"` is two actions, like `["say hi", "wait 20"]`, and blank lines are left out; any other control character is refused.
- Path arguments (`project_scaffold dir`, `dev_cycle project`, `structure_save file`, `world_summary diff`, `build_batch`'s `file=`, `pack file`, a `.png` `texture name`) are relative to the workspace and must stay inside it once `..` is applied; only `msc_workspace`'s `path` may name a folder anywhere. So `dev_cycle` builds only a project inside the workspace: to work on one elsewhere, switch to its folder with `msc_workspace`. A path the file system cannot hold (a control character, a name longer than 255 bytes, a character the platform refuses) is refused in one line naming the argument, before anything is written; a folder that cannot be created is refused in one line naming the folder and the reason. No tool answers `error: internal: ...` for bad input (`BadInputBehaviourTest` calls every tool with every string argument set to such values).
- Arguments are checked in one place, `ToolRegistry.call`, before the tool runs, so a refused call changes nothing, is logged and is counted in `msc_status stats=true` like any other: an argument the tool does not take is refused with the ones it does take (`error: unknown argument x; world_slice takes region, world, states, maxChars`), a missing required one with `error: missing argument: <name>`, a value of the wrong JSON type with `error: argument <name> must be an integer` (or a number, true or false, a string, an array of strings). Numbers and booleans may also come as strings (`"5"`, `"true"`). The MCP SDK's own schema check is off (#510), so no call is answered by it; the SDK still answers two requests itself, as JSON-RPC errors the MCP spec calls protocol errors: a tool name that is not in the list, and an `arguments` value that is not an object.
- A tool that picks a way refuses an argument that way does not read, in one line and before it does anything, instead of dropping it with an OK: `server_logs` by `mode` (`error: pattern is for mode=grep; add mode=grep or leave it out`; `lines` is for tail and grep), `texture` by rows, `kind`, `copy` or `animate`, `pack` by `check`, `build_batch` by `dryRun` (`physics` places nothing in a dry run), `msc_workspace` by `path` (`create`), `server_setup` by platform (`version`, `mode` and `acceptEula` are not for minestom or velocity), and every other tool that takes `acceptEula` by the same rule: `server_start` by the workspace's platform, `project_scaffold` by the template's.
- A number's range is declared once, in the schema's `minimum` and `maximum` (shown in the tables as `(integer, 1 to 100)`); a value outside it is refused with the range (`error: argument limit must be 1 to 100, not 101`), never clamped silently. The tables are generated from the same declaration, so the stated and the checked range cannot differ.
- Structure files: `structure_save` writes a Sponge schematic and takes only a `file` ending in `.schem` (any case). `world_summary diff=` and `build_batch`'s `file=` go by the content, not the name: a gzip file is read as a schematic, anything else as a UTF-8 text structure; a file that is neither is refused in one line naming it.
- Errors come back as `error: <what is wrong and what to do>` with MCP `isError` set. They never contain a Java stack trace.
- Coordinates are strings: a position is `"x,y,z"`, a region is `"x1,y1,z1 x2,y2,z2"` (two corners, inclusive, any order), an area is `"x1,z1 x2,z2"`.
- Block names may omit `minecraft:`. Properties use vanilla syntax: `oak_stairs[facing=north]`.
- `world` is optional everywhere and defaults to the server's first world.
- Every call is logged (see "Tool log").
- World and build tools fail at once with `error: the server is not running...` when the core has no server running and none was attached with `MSC_CORE_ADDRESS`, and with `error: the server is stopping...` once its server was asked to stop (by `server_stop`, `dev_cycle`, or a `stop` that reached the agent), also while the process is still exiting (#703). They wait (up to 30 s) for an agent only while the server starts or its agent reconnects. A server another session runs, or one an earlier session left running (after `server_detach`), is named in the refusal as `msc_status` names it: `the server running here (pid N) was left by an earlier session and has no connection to this one: server_start or dev_cycle restarts it under this session, server_stop stops it`. `server_command`, `server_detach`, `server_wait` and `player_test` give the same reason (#705). A `stop` only the agent announced (`server.stopping`) counts until the server exits or a new agent connects, and only as a hint: an agent also announces it when just the agent stops (Paper's `/reload`, a plugin manager disabling it, Minestom's `MscAgent.stop()`) and the server runs on. So `server_command` still types into the console then, and `server_stop` types `stop` unless `server_stop` or `dev_cycle` already did, so the server saves its world rather than being killed after 30 s (#729).
- <!-- tool-list -->The tool definitions (29 tools: names, descriptions, argument schemas) are 19,762 characters, about 4,941 tokens in every conversation before MCP framing.<!-- /tool-list --> `McpBridgeTest` fails if the tool list as the client receives it grows past 16,600 characters ([ADR 0019](adr/0019-smaller-tool-surface.md), [ADR 0023](adr/0023-texture-tools.md), [ADR 0057](adr/0057-plugins-from-modrinth-hangar-spigot.md), [ADR 0068](adr/0068-quality-bar-for-any-agent.md)).
- Results are text. The one exception is `world_render`, which adds one PNG image next to its text.

## Typical loop

`project_scaffold` once, `server_setup` once, then edit code and call `dev_cycle` until it reports `no errors or warnings`. Look names up with `api_search` instead of guessing. Look at the world with `world_summary`, then `world_slice`; build with `build_batch`, a whole build per call.

Results:

- `msc_status`: 6 to 8 lines: core version, workspace, platform, server state (`stopping` while this session's server is being stopped by `server_stop` or announced its own stop, `running, detached`, `running, left by an earlier session` with its pid, or `running under another session that is still running` with the server's and that session's core pid, ADR 0037), agent (`of a server started outside this session` when it is an attached one; `refused N agent(s) without this session's token (a server another workspace or an earlier session started)` after such a server's agent knocked, with how to take over this workspace's leftover when there is one, ADR 0050), API index, then one line per setup warning: the workspace is the MSC repo, and the install is older than its checkout or a newer install sits beside it. The same warnings go in front of the session's first tool result, worked out for the workspace that result is about (a first `msc_workspace` call that switches away from the repo gets no repo warning), inside its cap: they share it with the result, and a warning cut to its share ends `msc_status shows it all.` A warning the result already lists is not put in front again, so `msc_status` as the first call shows each warning once (#637). With `stats=true`, a table of this session's calls per tool instead.
- `msc_workspace`: 1 to 3 lines. Without `path`, or with the current one, 1 line (`workspace: <path>` or `workspace is already <path>`). A switch: `workspace: <path>`, then a line on what closing the old workspace did, only when it touched something: its dev server (`stopped the dev server of ...`, or that its detached server keeps running, with `could not start a standalone pack host (<why>), so nothing serves the resource pack until the switch back` when that host does not come up, and the same `; server.properties offers no pack ...` ending as `server_detach` when its offer was withdrawn; ADR 0051) and its test player (`the test player left`), joined by `; `, then `server folder: ...; platform: ...`, ending `; the server this session detached here runs on, still this session's` on a switch back to a folder whose server this session detached: the session keeps that server, its pack host and its agent connection through the switch, so world tools, `server_command` and `server_stop` reach it as before (#735). A switch that cannot open the new folder reopens the old one and errors with `could not open <path> (<why>); still in <old>`, then the same line on what the close did; when the old one cannot reopen either, the error says so and that `msc_workspace path=<old>` opens it again (#721). Until a switch opens a folder, `msc_workspace` without `path` and `msc_status` say `workspace: none open (<old> was closed; msc_workspace path=<old> opens it again)`, and a switch to that closed folder tries it once: `could not open <old> (<why>), so no workspace is open` (#727). A port that stays taken is named (`port N is taken: ...`). A fixed agent port (`MSC_CORE_ADDRESS`) is let go before the new folder binds it, and the bind waits up to 5 s for it, as the pack port's does. A switch into the MSC repo puts the repo warning in front of its result. Closes the old workspace like a session end and opens the new one; the server folder and tool log move along when they were the defaults. A relative `path` is relative to the current workspace.

Results:

- `project_scaffold`: 5 to 8 lines: where the project was created, its `projectId`, `packageName` and `version`, then for NeoForge and Forge a line that the first build started in the background, then the next step. Every next step names the `dev_cycle` call that builds this project: plain `dev_cycle` for the workspace root, `dev_cycle project=<dir>` for a subfolder (#665), so `next: edit the code, then dev_cycle project=lobby` after `dir=lobby`. `next: edit the code, then dev_cycle` when the server that runs the template is set up (the template's own, or the workspace's when it runs the same projects: Quilt for `fabric-mod`, Purpur or Folia for a Paper template, as `dev_cycle` deploys), or is the project itself (Minestom). Otherwise `server_setup` comes first: Velocity, which has no EULA, gets `next: server_setup platform=velocity, then edit the code and dev_cycle`; a server that needs the EULA (every platform but Minestom and Velocity) gets 1 line when the EULA is accepted for this machine, else 2 (the EULA question, then `On yes: server_setup acceptEula=true, ...`). Remembers the template's platform for the workspace when the scaffold goes into the workspace root or the workspace has none remembered yet, except over a workspace platform that runs the same projects (a Quilt workspace stays Quilt). A scaffold into a subfolder keeps the workspace's platform; when that platform's server does not run the template (another agent family, such as `fabric-mod` in a Paper workspace; [ADR 0048](adr/0048-one-server-per-workspace.md)), a line before the next step says so, `the workspace stays Paper, which never loads this Fabric project: server_setup platform=fabric switches it (Paper projects then need server_setup platform=paper)`, and the next step names `server_setup platform=<template's>` in every variant, also when that server's jar is already in the server folder. `template=paper-server` writes only server files (`server.properties`, `eula.txt`), no project: it never moves the workspace or gets that line, and its next step is for the workspace's own server (#643). A folder counts as empty when it holds only other tools' files (`.mcp.json`, `.claude`, `.git`, `.idea`, `.vscode`) and what MSC itself created there: `.msc` (caches, the pack's sources and build, backups, logs), the server folder (`run/` or `MSC_SERVER_DIR`) and the tool log (`MSC_TOOL_LOG`), so a scaffold into the workspace root works after `server_setup` too (#664). The project goes in beside them; a project template's `run/` files go into an existing server folder only where it lacks them, so the server's own `server.properties` and `eula.txt` stay. A folder that holds anything else is refused with what is in the way and `give dir=<new folder> to create the project beside them`. A project goes only where the other tools' next steps find it (#679): at most 4 folders deep (`dir=games/maze` is 2), and never inside MSC's own paths, `build`, `.gradle`, `node_modules`, `.git` or another tool's folder; such a `dir` is refused before anything is written (`error: dir a/b/c/d/e is 5 folders deep, ...`, `error: dir run/x is in run, where MSC never looks for projects ...`).
- `server_setup`: one line per step that has something to say, in this order: `wrote N default config files` (only the files the server folder lacked); with `mode`, `mode game: survival, normal difficulty from the next start` or `mode build: creative, peaceful difficulty from the next start`; the install (Paper `paper <version> build <n> (downloaded)` or `(cached)`; Purpur `purpur <version> build <n> (installed)` or `(already there)`; NeoForge and Forge `<name> <version> (installed)` or `(already there)`; Fabric `fabric launcher for ...` then `fabric api <version>`; Quilt `quilt loader <version> (installed)` then `fabric api <version>`); `agent installed in mods/` (or `plugins/`), or `warning: msc <agent> agent not found ...`, naming the agent the platform runs and the jar to put in `.msc/agent` (`msc-agent-paper.jar` for Paper and Purpur, `msc-agent-fabric.jar` for Fabric and Quilt); Paper or Purpur without Velocity forwarding, with Geyser wanted (`bedrock=true`, or a folder that has it): `geyser <version> build <n> (downloaded), floodgate ...` (or `(cached)`, `(already there)`; `geyser (already there)` for a jar kept while GeyserMC is down), `bedrock.port was taken, moved to N` when it was, and `bedrock: UDP <address>:<port> (Geyser, fronting Java port <port>; ...)`; `bedrock=false`: `removed Geyser and Floodgate from plugins/ (their config folders stay)`; the EULA: `eula.txt has eula=true from the owner's one-time acceptance for this machine (...)`, or `note: eula.txt has eula=true; ...` when the file already says so, or when it is not accepted two lines, `the Minecraft EULA is not accepted, so server_start refuses. Next: ask the user ...` and `On yes: server_setup acceptEula=true ...`; the first `acceptEula=true` adds `Minecraft EULA (...) accepted for this machine ...` before the EULA line; last `<platform> server ready in <folder>; next: server_start or project_scaffold then dev_cycle`, where the scaffold names the template the workspace's server runs unless that is `project_scaffold`'s default `paper-plugin` (Paper, Purpur, Folia), so following it never switches the platform (#689): `project_scaffold template=fabric-mod` on Fabric and Quilt, `template=neoforge-mod`, `template=forge-mod`, `template=minestom-server`, `template=velocity-plugin`; once the workspace has a project the `dev_cycle` step names it as `project_scaffold`'s next step does (`dev_cycle`, or `dev_cycle project=<folder>` for each folder with a Gradle wrapper up to 4 folders deep, such as `dev_cycle project=games/maze` (#679); MSC's own paths, `build`, `.gradle`, `node_modules`, `.git` and other tools' folders are not searched). Only a project the workspace's server runs is named, by the same agent-family rule `dev_cycle` refuses with (#680, [ADR 0048](adr/0048-one-server-per-workspace.md)). When the workspace's projects are all of another family, the step is a new project beside them and says why, with the switch: `project_scaffold template=minestom-server dir=<new folder> then dev_cycle project=<new folder>; proxy is a Velocity project, which Minestom never runs: server_setup platform=velocity switches the workspace to it` (`dir=<new folder>` whenever the workspace holds files that are not MSC's, where a scaffold into the root is refused). Minestom's and Velocity's last lines end the same way, and so does a Minestom `server_start` with no server jar yet (`Run <step> to build the project and put its jar there`). Minestom: `minestom needs no server download ...`. `mode=game` sets `gamemode=survival`, `difficulty=normal` and `force-gamemode=true` in `server.properties` (`mode=build`: creative, peaceful); without `mode` a new server gets build defaults and an existing one keeps its settings. Folia (ADR 0045): Folia `folia <version> build <n> (downloaded)` or `(cached)`, then `folia: plugins load only with folia-supported: true ...`. With `proxy` (Paper, Purpur, Folia), before the install line: `proxy velocity: players join only through the Velocity proxy ...` or `proxy none: players join directly`. Velocity: Velocity `velocity <version> build <n> (downloaded)` or `(cached)`, `wrote velocity.toml: ...` (or `velocity.toml kept as it is`), `backend: a paper, purpur or folia server set up with proxy=velocity, ...`, last `velocity proxy ready in <folder> ...`.
- `plugins`: `search=` gives up to 5 matches per source, one line each, `<id>  <name>: <description> (<downloads>)`, in each source's own order (Modrinth's relevance, Hangar's, SpigotMC's by downloads), then `install with plugins install=<id>`; Modrinth hits are server-side mods or plugins for the workspace's loaders, Hangar is asked on Paper-family and Velocity servers, SpigotMC on Paper-family only, premium SpigotMC resources are left out and externally hosted ones are marked. `install=` gives one `installed <id> <version> -> plugins/<file>` line per jar, required dependencies included, with `(made for Minecraft X, not Y; check the startup log)` when a plugin has no build for the server's version (a mod is refused instead) and `not installed: ...` for a dependency hosted elsewhere; an older jar with the same plugin id is replaced. The Minecraft version is the one `server_setup` installed (`run/.msc-minecraft`), else the default. With neither, one line per jar. Every call ends with `check: ok` or `problems:` and one line per jar that will not load: not a plugin or mod, built for another platform, a required dependency missing, or one id in several jars. `server_start` and `dev_cycle` print the same problems as `addon problem: ...` lines, except jars with no descriptor (a library a mod loader may still load). It never suggests what to install ([ADR 0057](adr/0057-plugins-from-modrinth-hangar-spigot.md)).
- `server_start`: up to 6,000 chars: `server ready in 8.2s, agent connected`, then `world world: ground is y=-61 (most common top block around 0,0; build from y=-60)` (dev worlds are superflat, far below y=64), then `mode: creative, peaceful difficulty (server_setup mode=game for survival, normal: ...)` from `server.properties`, then, with Geyser in `plugins/` where it works (Paper or Purpur, Velocity forwarding off), the `bedrock: UDP ...` line `server_setup` gives, plus startup warnings and errors only. A server that exits during or right after startup is reported as `server exited ...`, then its triage (below), then its warnings and errors. Fails at once with a one-line error, before it changes anything, if there is no server to start or `eula.txt` lacks `eula=true` and the EULA is not accepted for this machine (nor with `acceptEula=true` on this call). Replaces an installed agent jar that differs from the one in `.msc/agent` (or `MSC_AGENT_JAR`) first, and says `agent jar updated`. Just before the start, also removes what an interrupted earlier call left in `plugins/`, `mods/` or `libs/` (such as `x.jar.msc-removing` from older cores, which Quilt would load as a second copy of the mod) and says `removed N files an interrupted earlier call left`.
- `server_detach`: 2 or 3 lines: `server detached: ...` (`, and so does the resource pack host` only when one serves the pack past the session), then, when a built pack's host keeps running, `server.properties now offers the pack too, ...` where the server folder has a `server.properties` and the platform reads the pack from it, or on Minestom and Velocity, which do not, `<Platform> does not read the pack from server.properties, so a restart outside MSC does not offer it.`, then that world tools and `server_command` work until the session ends and that the next session stops the server (`and the pack host` only when one outlives the session; on Velocity, a proxy with no world, only `server_command`, and no world is saved; #722). While the server is detached, a standalone process serves the workspace's pack on the same port (pid in `.msc/pack-host.pid`; it serves each build by its hash from `.msc/build`, so a later build never takes an earlier URL away, ADR 0053), and `resource-pack`, `resource-pack-sha1`, `resource-pack-id` and `require-resource-pack` go into `server.properties`, so a restart outside MSC still sends it; on Minestom and Velocity nothing is written there, by this call, `pack` or a start (ADR 0017, #718). That holds whatever the order (ADR 0051): with a built pack (this session's last build, or the `.msc/build/pack.zip` an earlier build left, served as it is) this call does it, and with none yet (`(no pack built yet; the pack tool starts a pack host that does too)`) the first `pack` or `dev_cycle` rebuild after it does, and every later build goes to that host, so a switch away, the switch back and the session end leave the pack served (#741, #743). A host that does not come up never fails the call: the line after the first says `could not start a standalone pack host (<why>), so the resource pack is served by this session only, until it ends`, nothing new goes into `server.properties`, and the next `pack`, `dev_cycle` or switch tries again (#744). An offer of this workspace's pack already there (an earlier detach's, which every start keeps pointed at the build) is withdrawn then, as a restart outside MSC after the session would get a URL nothing serves, and the line ends `; server.properties offers no pack until a standalone host serves it`; the next publish whose host comes up offers it again (#747). Every line on the pack host and the offer, here and in `pack`, `dev_cycle` and `msc_workspace`, is made from whether a standalone host serves the pack past the session. The server keeps this session as its owner: while this session runs, another session's tools refuse to touch it (ADR 0037). Once it ends, the next `server_start`, `dev_cycle` or `server_stop` stops both, the server over RCON; the next start serves the pack again on the same port and updates `server.properties` (or clears it if the pack is gone). Until then the next session publishes the server's pack as this one does while it is detached: a `pack`, a switch away or that session's end reuses the pack host (or replaces one that no longer serves the build) and keeps the offer on it (#750).
- `server_stop`: 1 line. Also stops a server an earlier core left running (pid and start time in `.msc/server.pid`, with the pid and start time of the core that started it), as `server_start` and `dev_cycle` do first: over RCON so it saves (at `server-ip` and `rcon.port` from `server.properties`, read as the server reads them), killed only if that fails. The pid file stays until that server is gone. A leftover that survives the kill is an error naming its pid, what was tried and how to stop it by hand; while it runs, `server_start` and `dev_cycle` refuse too (a new server could not take its world or port, and its pid would replace the leftover's record), and only kill it again briefly instead of waiting the whole stop out again (`resisting` in the pid file). `server_stop` tries the whole stop again each time. A server and the pack host that serves it end together: `server_start`, `dev_cycle` (also with `restart=false`) and `server_stop` that stop a leftover also stop its pack host (`stopped the pack host left running by an earlier session (pid <pid>)` when it ran), and a pack host left running after its server exited is stopped by the next publish or the session end (ADR 0053, #752). A server whose core still runs (another session open on the same workspace) is no leftover: `server_start`, `server_stop`, `dev_cycle` and `server_setup` then refuse in one line naming that session's core pid (use that session, or end it) and change nothing (ADR 0037). A pid file from cores before that names no owner and is a leftover as before. Every change a core makes to the pid file (a start's check, launch and record; a stop's delete; a leftover's claim) is made holding a short lock on `.msc/server.lock`, so two sessions starting at the same moment launch one server and the other is refused as above; a call that waits over 10 s for another session's start or stop refuses in one line and changes nothing.
- `dev_cycle`: up to `maxChars`. Gradle builds only the deployable jar (`mscJar`, added by `.msc/msc-init.gradle`; on Minestom a thin `server.jar` plus `libs/`), then the tests (`check`) run while the server restarts. A jar identical to the one the running server loaded is not redeployed and the server keeps running, with or without `restart=false` (#681): the jar keeps its file time, so a later `dev_cycle` does not restart for nothing. When the server it restarts would refuse to start (the EULA not accepted), it refuses at once with that one-line error, before building or changing anything. A project the workspace's server does not run (none of the platforms it is made for is of the remembered platform's agent family: a Fabric mod in a Paper workspace) is refused the same way, `error: foo is a Fabric project, but this workspace runs Paper, which never loads it; nothing was built or deployed. server_setup platform=fabric switches the workspace to Fabric (...), or msc_workspace gives the project its own workspace.` ([ADR 0048](adr/0048-one-server-per-workspace.md)). A folder with no Gradle wrapper is refused with the step that works: `dev_cycle project=<folder>` for each project below it that the workspace's server runs, searched as `server_setup`'s last line is (#665, #679, #680), else `Run ` and that line's step (`Run project_scaffold then dev_cycle.`, with the workspace's template as there: `Run project_scaffold template=minestom-server then dev_cycle.`) dev_cycle does not pick a subfolder project by itself: which project it builds is always the one `project` names. On a failed compile: compiler errors. Failed tests come first (`TESTS FAILED`, with `(the new jar is deployed anyway)` only when this call deployed it; an unchanged jar's line says it was kept). Whenever the call leaves a running server running (an unchanged jar, `restart=false` with a changed jar, or a build with no jar), the workspace's pack is rebuilt and sent (`resource pack sent: players who join get it`) only when it differs from what the running server's agent connection was last sent; otherwise, and on a proxy, which has no agent, nothing is said about it (#667, #690, #694). A restart's new connection always gets it. Then startup warnings and errors, or `no errors or warnings`, and a last line `time: jar, stop, start, agent, tests, total`. A cut of its own lines, or its `[N of M outputs cut to fit. ...]` line, names only what shows what was cut: `Failed tests: <project>/build/test-results.` when this run's tests wrote results there, `Startup log: server_logs.` after a start, then raising maxChars below 24,000.
- `server_logs`: up to `maxChars`; see "How logs are condensed" and "How crashes are triaged" below.
- `server_command`: up to 6,000 chars. A command with bad syntax fails with the parser's message (`command failed`, then where it stopped). Lines the server console printed while the command ran (broadcasts such as `/say`, which never reach the sender) follow under `console during the command:`.
- `server_wait`: 1 to 6 lines: `matched after 4.1s: <line>`, or `no line matched in 60s` (or `the server stopped after ...`) followed by up to the last 5 new lines. Looks at lines since the last `server_command`, `server_wait` match or start, so a line printed between two calls is not missed and one line never matches twice. Not an error on timeout. `timeoutSeconds` is at most 600. Only for a server this core started.

How logs are condensed: the dev server's fixed banners (running as root or administrator, offline mode, which MSC sets: the server's, a backend's behind the Velocity proxy, and Velocity's own) and the Windows system-report noise (`[oshi.*]` messages, `Failed to get system info for ...`) are dropped. Otherwise only WARN and ERROR entries and anything with a stack trace are kept. In a trace, the exception lines, the first frame and all frames outside framework packages (`java.`, `net.minecraft.`, `org.bukkit.`, `io.papermc.`, the mod loaders' `net.fabricmc.`, `net.neoforged.`, `net.minecraftforge.`, `cpw.mods.`, Velocity's `com.velocitypowered.`, Minestom's `net.minestom.`, Geyser's `org.geysermc.`, Mixin and similar: each platform's own packages) are kept; runs of framework frames become `... N framework frames`. Identical entries are shown once with a count. By default `server_logs` looks only at lines since the last start.

How crashes are triaged (`server_logs mode=triage`, and `server_start` and `dev_cycle` when the server exits; [ADR 0040](adr/0040-crash-triage.md)): at most 3 findings, each a few lines: what died and where it was read (`[log 12:00:02]`, a crash report's file name), `culprit:` (the first frame outside JDK, server and loader packages, or `server or loader code`), `cause:` (the root exception: the last `Caused by`), up to 3 key frames, and a one-line `fix:`. It reads the log since the last start (the whole buffer with `all=true`; `logs/latest.log` when the buffer is empty), the newest `crash-reports/crash-*.txt` and the newest `hs_err_pid*.log` written since the last start (any with `all=true`). Known causes come first, from the messages each platform prints: the EULA, the server's port in use (`FAILED TO BIND TO PORT`, or a bind under server code; the fix names `server-port` in `server.properties`, on Minestom the main class's `server.start(...)`; when an MSC pack host holds the port, `server_start` and `dev_cycle` name it instead, by its pid, and this session's own host moves to a free port: `this session's resource pack host held port N and has moved to a free one: start the server again`, ADR 0054; a port a plugin or mod binds itself is that code's exception), out of memory, a wrong Java version, a missing or wrong-version dependency (Paper and Purpur, Fabric and Quilt, NeoForge and Forge), a plugin that failed to enable or load, a mod whose entrypoint, constructor or mixin failed, the watchdog. A known cause with no plugin or mod frames is one line and its fix. Otherwise the fatal or uncaught exception, or with none the last logged exception (`not fatal`). A crash report that holds the log's exception joins its finding; repeats are counted (`(x2)`). Nothing found: `no crash or startup failure found in N log lines and no new crash report; server running` (or `not running`), or `... in N lines of logs/latest.log ...` when it read that file. Repeats are counted on every platform, Minestom's untimed lines too.

### Platforms

The workspace has one platform: `paper` (default), `purpur`, `folia`, `fabric`, `quilt`, `neoforge`, `forge`, `minestom` or the `velocity` proxy ([ADR 0027](adr/0027-more-platforms.md), [ADR 0045](adr/0045-folia-and-proxies.md)). `project_scaffold` into the workspace root, or into a workspace with none remembered, remembers the template's platform in `<workspace>/.msc/platform`; `server_setup platform=...` sets it, and so does a project's first `dev_cycle` in a workspace with none. Without any of these the core looks at the project files, first match wins. First the descriptor the server loads, in `src/main/resources` or `src/main/templates` (the NeoForge MDK's), or the Gradle plugin that writes it: `quilt.mod.json` is Quilt, `fabric.mod.json` Fabric, `META-INF/neoforge.mods.toml` NeoForge, `META-INF/mods.toml` Forge, `paper-plugin.yml` or `plugin.yml` Paper (also written by plugin-yml's `bukkit`/`paper` plugin or block, or resource-factory's Bukkit or Paper convention), `velocity-plugin.json` Velocity. Then the platform's Gradle plugin in `build.gradle(.kts)` or `gradle/libs.versions.toml`: Quilt or Fabric Loom, ModDevGradle (its `legacyforge` plugin is Forge) or NeoGradle, ForgeGradle, paperweight or run-paper, run-velocity. Last a dependency: `velocity-api` Velocity, Minestom. So a plugin built for both Paper and Velocity is Paper, but it runs on every platform whose sign it shows (Minestom only when nothing else shows): a Velocity workspace deploys it too (#642). Build text that a longer sign of another platform covers is that platform's only: `net.neoforged.moddev.legacyforge` is Forge, not NeoForge too (#648). Purpur and Folia cannot be told from a Paper plugin, so they are only ever the remembered platform; `dev_cycle` keeps a remembered Purpur, Folia or Quilt for a Paper or Fabric project. A workspace runs one server: `dev_cycle` refuses a project that runs on no platform of the remembered platform's agent family until `server_setup platform=...` switches it ([ADR 0048](adr/0048-one-server-per-workspace.md)).

## Testing a game

- `server_setup mode=game` before testing combat, damage or hunger: the default dev server is creative and peaceful, so mobs despawn and players take no damage.
- `world_entities` checks wave spawns, NPCs and holograms (text displays) without a player.
- `server_wait until="Wave 3"` waits for a log or chat line instead of polling `server_command`. Log what the game does (stage changes, wins, losses) so it can be waited for.
- `server_command "tick sprint 600"` runs 600 ticks (30 game seconds) as fast as the server can, so timers and waves come sooner. `tick rate 40` doubles the speed; `tick rate 20` restores it.
- Chunks with no player nearby are not loaded, so nothing in them moves: mobs spawned there freeze and redstone stops. Keep game areas loaded with a plugin chunk ticket (Paper: `world.addPluginChunkTicket(chunkX, chunkZ, plugin)`) or `forceload add x1 z1 x2 z2`. Vanilla spawner blocks and natural spawning also need a player close by, so spawn waves from the plugin.


## Text structure format

Used by `world_slice` (output) and `build_batch` `structure` steps (input), so a slice can be edited and written back.

```
legend: .=air #=stone_bricks g=glass
y=64
#####
#...#
#####
y=65 same as y=64
y=66 all #
```

- One character per block. Rows run from the lowest Z (top row) to the highest; columns from the lowest X (left) to the highest.
- `.` is air and `_` means "leave unchanged", unless the legend redefines them.
- Layers are listed by Y. In a `structure` step the numbers only give the order: the lowest layer is placed at the step's position.
- `y=N same as y=M` repeats a layer; `y=N all #` fills a layer with one symbol or block.
- Symbols are handed out by frequency. With `states=false` (default) blocks that differ only in properties share a symbol.
- `data X,Y,Z {SNBT}` gives the block there its block entity data, as `world_slice data=true` writes it. X and Z count from the `region` line's lowest corner when the text has one (a pasted slice does), else from 0 (first column, first row); Y is the layer number. The cell must hold a block, not `_`. Data turns with its block under `rotate`.

`build_batch` answers `edit eN: <count> blocks changed, region <box>`, plus a `blocks:` line when it placed more than one kind, for up to 8,388,608 blocks. The id undoes the whole edit, even when the core split it into several agent calls; an id lasts as long as the server run that made it (a `server_stop`, a restart or a server that stops on its own ends it: `unknown edit eN`), and the server keeps only the last 8,388,608 changed blocks across all edits, so the oldest edits can be undone only partly (`undid eN partly: ...` says how many parts were lost). If an undo stops half-way while that run goes on (a timeout), the same id undoes the rest. A build or undo cut off by its server stopping (or crashing) names no id and no count: the part in flight may be half applied and what stays is what the server saved (Minestom saves only on stop), so it says the box may be partly changed, by an amount that depends on what the server saved, then the way back: `world_summary` there to look, `build_undo backup=` if a backup exists, or a `build_batch` over it ([ADR 0049](adr/0049-undo-out-of-order.md), #708). Builds and undos run one at a time per server, so a build sent while another runs reads the world (`replace=`, `copy`) as that one leaves it. Any edit can be undone, not only the latest, unless a later edit still applied set some of the same blocks: then nothing changes and the answer names those edits to undo first, newest first (`e1 not undone: later edit e2 set some of the same blocks, ... Undo it first (build_undo edit=e2), then e1.`, [ADR 0049](adr/0049-undo-out-of-order.md)). An undo puts back block entity data too (sign text, container items) on every platform.

Block entity data ([ADR 0042](adr/0042-block-entity-data.md)): any block in a step may end in SNBT, as `/setblock` takes it: `set 3,-60,5 chest[facing=east]{Items:[{Slot:0b,id:"minecraft:diamond",count:3}],CustomName:'"Loot"'}`, `fill ... spawner{SpawnData:{entity:{id:"minecraft:zombie"}}}`. The core checks the SNBT first (`bad SNBT at character N: ...`, nothing placed) and drops `id`, `x`, `y` and `z`; the agent refuses data on a block that keeps none (`stone has no block entity data`). The data is merged into the placed block's data as `/data merge block` does, also where the block was already there, and the edit's undo puts the old data back. `copy` and `structure_save` keep block entity data (a schematic writes it as Sponge `BlockEntities`, with the block's id as `Id`), and a `structure` step from a `.schem` file (version 2 or 3) places it. `world_summary diff=` compares blocks only. Entities and items are not part of this: on every platform but Minestom, `server_command` reads and changes them with the game's own commands (`data get entity <uuid>`, `data merge entity <uuid> {...}`, `summon`, `give`, `item replace`); `world_entities ids=true` gives the UUIDs. Minestom has no entity or item NBT for the core to edit: the project's code makes them. `copy` reads the world before the call, so source and target may overlap. See [ADR 0015](adr/0015-build-batch.md) and [ADR 0019](adr/0019-smaller-tool-surface.md).

Undo ids do not survive a restart. For that, `build_undo backup=` keeps whole-world backups in `.msc/backups` (newest 5, within 2 GiB): `list` shows them (`<name> (<world folders>; <size>)`), `save [label]` takes one (`save-off`, `save-all flush`, copy, `save-on`; the world of a stopped server as it is; refused like the world tools while a server another session runs, or an earlier session left running, is up, #709), and a name (or a part only one name has; blank or ambiguous is refused) rolls the world back: `rolled back to <backup>`, `the world before it is backup <name>`, the stop note of a server an earlier session left running, as `server_start` gives it (that server counts as running, so it starts again), then the server's start report, or `server not started (it was not running)`. A `build_batch` of 100,000 blocks or more takes one first, unless one is younger than 5 minutes, and ends with `backup <name> taken first (build_undo backup=NAME restores it)`. A world folder is any folder in `run/` holding a `level.dat`, a `region/`, or a `dimensions/<namespace>/<name>/region/` (the Minestom templates' `world`); with none, `save` is refused. Minestom saves its world only on stop, so a backup of a running Minestom server is the world as last stopped. See [ADR 0041](adr/0041-world-backups.md).

Results:

- `texture`: writes the PNG, plus a model and item definition so the texture is usable through the `item_model` component, and prints that id. The default namespace is `msc`. Generate also returns a stats line (size, colors, opaque share, main hue) and the palette text, unless it is animated in the same call. Draw warns about odd sizes and large palettes. Recolor maps the source's colors, darkest to lightest, onto a ramp of `color`. Animate replaces the still texture with a frame strip and writes its `.png.mcmeta`, starting from frame 1 if it was already animated; writing a still texture over it later removes the `.mcmeta`. Two ways in one call is an error. So is an argument the chosen kind does not read: seed and size are for patterns, accent for ore, bricks, sword, pickaxe and food.
- `texture_view`: about 80 tokens for 16 x 16; a large texture is cut at `maxChars` (6,000 by default) like any result. An animation shows `frame 1 of N` and that frame only.
- `model_create`: writes the model and, unless `item=false`, an item definition named after it. `textures` is either one bare name, which fills every slot, or `slot=texture` for every slot of the kind, each once (#691): `cube_all` has `all`; `cube_column` `end`, `side`; `cube_bottom_top` `top`, `bottom`, `side`; `orientable` `front`, `side`, `top`; `cross` `cross`; `item` and `handheld` `layer0`. Anything else is refused before anything is written, quoting only what the call wrote: a slot the kind lacks (`error: orientable has no texture slot "frnt"; slots are front, side, top`), a slot left out (`error: orientable needs textures for front, side, top; missing side`), a slot given twice (`error: slot front is given twice`), or a bare name beside other entries (`error: "item/ruby" names no slot: give either one bare texture, which fills every slot, or slot=texture for each of all`).
- `pack`: zips the pack (same content gives the same SHA-1). The agent also sends it to players who join later. The pack belongs to the workspace, not the session: a build with `apply` (the default) is kept as the workspace's pack to send (`.msc/pack-applied.json`), whether or not an agent was connected, so every later start that connects an agent, by `server_start` or `dev_cycle`, in this session, after an `msc_workspace` switch away and back, or in a later session, serves and sends it (`resource pack sent: players who join get it`), and so does an agent that says its server is ready after the start was reported. A `dev_cycle` that keeps the server running sends it only when it differs from what that connection was last sent. With no agent connected, `pack` says so and names that step (`not sent yet: no server agent connected; the next server_start or dev_cycle sends it`); on a proxy it says why none will connect. While the server outlives the session, the build is served by the standalone host and `server.properties` offers it (`server.properties updated to offer this build`), also when the detach came first (#743); once the file offers an MSC pack it is pointed at every new build. A server outlives the session when this session detached it, and also when an earlier session left it running and no `server_start`, `dev_cycle` or `server_stop` has taken it over yet: that session's pack host is reused when the host on the port recorded with it (`.msc/pack-host.id`) answers that host's pid and token and serves the build, and the URL then names that port, else it is replaced on this workspace's port, so the offer always names a URL a host that outlives the session serves, or none (#750, #756, ADR 0054). A server another live session runs keeps its offer as that session wrote it, and keeps serving every URL that session offered or sent: each build is also written as `.msc/build/pack-<sha1>.zip`, a file never rewritten, which the standalone host serves by that name, so no later build, in this session or another, takes an earlier build's URL away; this session then serves its own build itself, on a free port at once (ADR 0053, #753). Build files that nothing offers, sends or serves any more are deleted after the next publish. When that host does not come up, the pack is still served and sent, by this session only, and a line says why (`could not start a standalone pack host (<why>), so the resource pack is served by this session only, until it ends`, #744), ending `; server.properties offers no pack until a standalone host serves it` when the file offered this workspace's pack and no longer does (#747); dev_cycle's rebuild adds the same line. Ends with the `msc-textures` `PackLint` summary (files, errors, warnings, notes) and the first findings, such as a model pointing at a missing texture. `check=true` only lints the pack sources; a missing `pack.mcmeta` is not reported before the first build, which writes it.
